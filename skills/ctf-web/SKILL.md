# ctf-web

## 适用范围与排除

分析获授权的 HTTP 应用题。排除未授权站点、真实账户或生产数据。

## 输入与前置检查

输入包含授权来源、路径、可用的合成身份和固定预期。核对授权范围、端口与协议。业务明确授权的非回环目标需要后续批准的执行能力。

## 离线协作

1. 保留 Web 分类。读取题面、源码和附件，记录框架、路由、认证条件和输入来源。标出对应源码位置，并将观察事实与待验证假设分开。
2. 需要用户补充常规 HTTP 行为证据时，列出方法、URL、请求头、参数、请求体、验证目的和预期观察；没有的字段写“无”。只提出正常客户端会发送的请求或防御性检查，使用合成身份和凭证占位符。标记“待用户执行”，由用户决定是否执行。
3. 接收用户提供的原始请求和响应、Burp 导出、浏览器网络记录、截图或附件。记录来源与捕获时间（若已知），核对状态码、响应头、Cookie 属性、正文、错误和参数差异。遮盖凭证值；对截图或截断记录，标明看不到的字段。
4. 按新证据更新假设为“支持”“排除”或“待验证”，保留已有基线。只提出能区分剩余假设的下一项常规检查；若没有实际响应，记录缺失证据。
5. 分别标注候选问题、源码已确认的行为、HTTP 观察、用户提供的靶场验证和 Flag 验证状态。待执行方案不产生 HTTP 证据。Gateway 返回的 LOCALLY_VERIFIED 仅代表本地验证；平台接受需要平台证据。

## 分析流程

开始时记录题名、题面和已有附件中的识别线索。赛事归属没有证据时标为待确认，并遵守用户对查找题解的限制。

对每条负面观测，写清同时成立的其他解释及观测范围。例如，脚本未读到 Cookie，只能确认该页面上下文未读到脚本可见的 Cookie。计划开展批量检查前，写明要区分的假设和停止条件。连续检查只重复已有结论时，回到现有证据重新排序。

先记录基线请求和响应。逐次只改一项输入。分别核对身份、对象归属和操作权限。SQL 注入比较错误和布尔差异，XSS 先判断渲染上下文，SSRF 用回环回调证明出站边界。检查上传类型、保存路径及下载授权，检查业务顺序和重复提交。

## 工具与中间证据

当前通过 web-local 发回环请求。curl 只作为后续经验证的候选。保留授权记录、请求摘要、状态码、响应摘要和操作 ID，避免记录 Cookie 或密钥。

## 误判、验证与停止条件

组件名称或版本只用于确认环境。若检查结果互相矛盾，保留待验证状态，并记录哪项观测与假设冲突。目标端口变更或出现 502 时，重新建立基线，标明新旧实例各自的观测。

重定向、范围变化或触及真实数据立即停止。通用错误、页面回显和缓存差异不足以证明漏洞。用固定预期或最小独立对照确认结果，再验证 Flag。
